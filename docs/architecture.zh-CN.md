# 架构与设计

## 模型

框架分为四层：

1. **能力目录**：部署方维护能力名称和说明。只有目录中的能力可以被注册，业务代码决定如何实现。
2. **调度器**：PostgreSQL 是 Worker、任务、尝试、事件、配额和共享事实的事实源。每次状态变更使用短事务，并按 schema 加 advisory lock。
3. **Worker 边界**：Worker 使用只绑定一个能力的凭据。先注册再领取，执行时续租，并使用 `call_id` 回传结果。
4. **业务适配层**：处理函数读取任务输入和依赖事实，访问真实系统，并自行负责鉴权、幂等和审计。

## 生命周期

正常流程是 `register → claim → heartbeat → result`。领取任务会创建尝试，并绑定 `agent_id`、`attempt_id` 和 `call_id`。只有绑定仍指向当前运行中的尝试时，调度器才接受回执。取消先标记任务为取消，保留运行中尝试及执行额度，直到确认停止或租约过期；租约过期时结束尝试并释放额度。两条路径都会阻止迟到回执覆盖新状态。

## 任务图

客户端提交请求编号和 JSON 任务图。框架先复制调用方对象，按确定顺序规范化，然后检查重复 ID、悬空依赖和循环，最后在第一次写入的同一事务中检查能力目录。相同请求编号和相同规范化任务图可重复提交；改变任务图会拒绝。

## 信任边界

管理端凭据可以查看状态、提交和取消任务。每个 Worker 凭据只允许声明的能力。凭据必须由部署生成、放在仓库之外并定期轮换，不能放进任务输入。HTTP 层只返回稳定的错误类别，不泄露数据库驱动异常、连接字符串或任务内容。框架无法证明处理函数的业务授权，外部副作用前必须由业务适配层再次鉴权。

## 恢复和运维

租约使进程崩溃可以恢复。`tick()` 先回收过期尝试，再删除过期注册；每个任务的重试次数受 `max_attempts` 限制。应备份 PostgreSQL，并监控 `agent_events`、失败尝试、队列等待时间、租约过期率和处理延迟。每个部署使用独立 schema 和最小权限数据库账号。

## 扩展契约

增加能力目录项，实现处理函数，然后提交任务图。不要为业务状态复制调度器；业务记录应留在自己的 schema，任务输入只引用其标识。若需要其他传输层，可把它适配到相同的调度器方法，并保留 `agent_id`、`attempt_id` 和 `call_id` 的语义。
